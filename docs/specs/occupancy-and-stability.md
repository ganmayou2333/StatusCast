# Spec: 占用基线与稳定性加固

状态：参数已与用户逐条确认（2026-11-07），实施中
前置：`docs/test-reports/v3.4.0-bug-hunt.md`（6 个缺陷已修）
关联：[GLOSSARY.md](../../GLOSSARY.md)、`docs/adr/0001-control-surface-static-token.md`

## 背景

用户诉求是「优化项目占用、修 bug、提高稳定性」。先量化再动手，实测结论与直觉不符：

| 指标 | 实测 | 判断 |
| --- | --- | --- |
| 固件 flash | 1,381,061 B / 5 MB 分区 | 74% 空闲，**不是瓶颈** |
| 固件 DIRAM | 191,855 / 341,760（56%） | 剩 150 KB，主要是 WiFi/BT 协议栈 |
| Python 单轮 | 0.51 s（30 s 周期） | 占周期 1.7% |
| daemon 常驻 | Release 49.3 MB workingSet / **private 14.0 MB** / 26 线程；Debug 49.8 / 13.8 / 25 | **Release 与 Debug 无差别**，是运行时基线 |
| 发布体积 | 0.21 MB（单文件、框架依赖） | R2R 反而 +38%，压缩不支持框架依赖 → **无处可优** |
| 固件按轮堆分配 | 4 处，全部在每条路径上释放 | **无按轮泄漏** |
| daemon 跨轮内存 | last-good 列表整体替换、HttpClient 单例 | **无跨轮增长** |

所以「占用」不是危机。真正的问题是**稳定性缺口**：轮次可以远超周期而不被察觉。

## 实测出的稳定性缺口

| 缺口 | 数字 | 后果 |
| --- | --- | --- |
| 固件单轮最坏 | **≈84.6 s**（LAN 29.6 + BLE 25 + PC ≤30，串行） vs 30 s 周期 | 超过周期；轮次串行 → 期间快照停止更新 |
| 固件看门狗 | 30 s 超时、**只查 idle 任务**、`PANIC` 未开、无任务订阅 | 卡死既不记录也不重启，`/health` 继续把旧数据报成最新 |
| 固件无界等待 | 3 处（BLE 轮次信号量 `portMAX_DELAY`、串口 paste 循环、`/control/*` 请求体 `continue` 重试） | 「单轮卡死」的真实入口 |
| Python 最坏单轮 | Android **≈185 s** vs daemon 30 s 强杀 | 一条路径失败 → 整轮被杀 → **所有**设备变 stale |
| PC 侧无界累积 | `console_state.json` 的 `failStreak` 与 key 集合从不清理 | 极小但确实无界 |

## 判据

每条都配可执行验收，口径仅限**静态审计 + 短时多轮**（用户已确认不挂机、不加速 soak）。

**R1 固件单轮有硬上限。**
每轮计算 `budget = clamp(周期秒*1000 - 2000, 3000, 25000)`；`deadline = 轮次开始 + budget`。
LAN / BLE / PC 三个阶段都必须在 deadline 前收手，且**已完成的结果照常发布**。
验收：`sc_round_budget_ms()` / `sc_deadline_reached()` 的 host 单测覆盖边界值（5 s、30 s、3600 s 周期）；
三个阶段各有一处 deadline 检查点，代码可审阅。

**R2 三处无界等待全部有上限。**
BLE 轮次信号量 ≤ 20 s；串口 paste 循环空闲 ≤ 60 s；`/control/*` 请求体整轮 ≤ 5 s。
验收：每处都是显式常量 + 超时后的降级路径；能 host 测的部分写单测。

**R3 `sc_sched` 订阅看门狗并开启 PANIC。**
`CONFIG_ESP_TASK_WDT_PANIC=y` 与 `CONFIG_ESP_TASK_WDT_TIMEOUT_S=30` 写进 `sdkconfig.defaults`
（不是仅 `sdkconfig`）；`sc_sched` 在轮次结束与每个 deadline 检查点喂狗。
验收：编译产物含 `esp_task_wdt_add` 调用；**真机重启行为未验证**（板子当前不在枚举中）。
风险：25 s 预算 + 30 s WDT = 5 s 余量，**依赖 R1 真的生效**，否则可能出现重启循环。

**R4 Python 有轮次 deadline。**
`status_core.py` 计算 `25 s` 预算（< daemon 30 s 强杀），批次之间与批次内检查；
超时采集器产出一条 `error` 行说明「采集预算用尽」，**其余已完成结果照常返回**。
验收：注入一个慢采集器，证明返回值是「部分结果 + 单条超时错误」，而不是进程被杀。

**R5 PC 侧只做护栏，不做优化。**
每 10 轮记一行 `[MEM] private=… threads=… handles=…`；private > 96 MB、线程 > 64、
或**最近 5 次采样**单调上升时打一条告警。**不新增 HTTP 端点**。
由于采样每 10 轮一次，「5 次采样」等价于约 **50 轮（25 分钟）**的持续增长窗口——
这是刻意的：泄漏检测不需要逐轮敏感，而逐轮采样会把 GC 抖动误报成趋势。
验收：短时 20 轮（5 s 间隔）跑完无告警、指标不增长；增长告警由单测覆盖（端到端跑不满 5 次采样）。

**R6 证据口径明写。**
小时~天级的长时间退化**未被证明**。任何报告只写「R1–R5 通过 + 长跑未验证」，
不得写成「稳定性已提升」。

## 参数

| 参数 | 值 |
| --- | --- |
| 轮次预算 | `clamp(周期ms − 2000, 3000, 25000)` |
| BLE 阶段预算 | 8 s（原 20 s） |
| PC feed 默认 | 5 s（不变）；**生效值再被剩余预算截断** |
| LAN | 每台主机、每个 TCP 端口前检查 deadline |
| 看门狗 | 30 s，`PANIC=y`，喂狗点在轮次结束与每个 deadline 检查点 |
| 无界等待 | BLE 20 s / paste 空闲 60 s / body 5 s |
| Python 预算 | 25 s |
| 护栏阈值 | private 96 MB、线程 64、连续 5 轮单调上升；每 10 轮记基线 |

## 非目标

- 不做 TLS、不改 `/control/*` 鉴权模型（见 ADR 0001）
- 不改 schema 3 契约、不改 `/status/` `/health` 语义
- 不新增 HTTP 端点
- 不优化固件 flash/DIRAM（实测宽裕）
- 不追求 private bytes 低于当前 14 MB

## 风险

1. **看门狗 PANIC 会把卡死变成重启**。板子无人值守时这是想要的；但若 R1 的 deadline 有 bug，
   表现会是重启循环——所以 R1 必须先于 R3 完成。
2. **收紧预算会让「慢但正确」的场景变成超时**：BLE 8 s 在心率带等首帧时可能不够。
   超时后的表现是「本轮未探测」而非错误，可在下一轮补上。
3. **短时多轮不能证明长跑**。R6 就是为此写的。
