# Bug hunt — v3.4.0 contract and firmware core

日期：2026-11-07
对象：`main` @ `4fb1e88`（v3.4.0）
方法：黑盒探测真实 daemon + 对不依赖 ESP-IDF 的固件 core 写对抗性用例 + 逐条核对文档承诺
失败测试：[`test/bug-hunt`](https://github.com/ganmayou2333/StatusCast/tree/test/bug-hunt) 分支（`aaaf97e`）

## 结论

**发现 6 个缺陷**：固件 core 4 个（其中 2 个会造成静默数据丢失或永久陈旧）、固件与 daemon 的判定分歧 1 个、文档承诺与 HTTP 栈实际行为不符 1 个。

三层里质量分布很不均匀：

| 层 | 结论 | 证据 |
| --- | --- | --- |
| Python 采集层 | **未发现缺陷**，文档所述行为逐条对上 | 195 项单测通过 + 24 项针对性探测 |
| C# daemon | **1 个文档缺陷**（F6），逻辑面干净 | 43 项单测通过 + 31 项黑盒探测通过 |
| 固件 core | **5 个缺陷**（F1–F5），全部在边界条件上 | 193→200 项检查，6 处红 |

风险集中在一处：**固件的容量规划**。两个独立的 8192 常量、一个 448 字节的透传缓冲、一个 96 字节的字符串上限，都没有和它们实际要承载的数据量对齐，而超限时的表现是**静默丢弃**而不是报错。

## F1 — 快照容量：9 台设备就撑爆，整轮不发布

**症状.** 配置到第 9 台带 `nekotrak` 的胖设备后，固件这一轮渲染失败并直接 `return`，**不发布快照**。表现取决于之前有没有成功发布过：有则永远返回上一轮的旧快照（`generatedAt` 不再前进），没有则 `/status/` 与 `/health` 永久 503。两种情况下串口都只有一行 `snapshot too large for the 8192 byte buffer`，HTTP 面完全看不出一致性问题。

**实测**（`harness2` 容量扫描，fat = 带 447 字节 nekotrak 子树）：

| 设备数 | 渲染字节 | 装得进 8192？ |
| --- | --- | --- |
| 7 | 6776 | 是 |
| 8 | 7737 | 是 |
| **9** | **8698** | **否** |

不带 nekotrak 时 16 台只要 4401 字节——`SC_MAX_DEVICES = 16` 这个上界只在「没有 nekotrak」时成立。

**最小复现.** `host_test/test_main.c::test_bug_snapshot_capacity` —— 9 台设备各灌一个 `SC_RAW_JSON_LEN` 长的 pet 子树，用 `char buf[8192]` 渲染，断言 `len != 0`。当前实测 `len == 0`，`sc_snapshot_render_len()` 需要 ~8545。

**根因.** `main/core/sc_core.h` 的 `SC_MAX_DEVICES` 与 `Kconfig.projbuild` 的 `CONFIG_SC_MAX_SNAPSHOT_JSON` 是两个互不知情的上界。更麻烦的是 `main/net/http_server.c` 里还有第三个 8192（`SC_BODY_MAX`）——它们目前**恰好相等**所以没有二次事故，但没有编译期约束：把 Kconfig 调到 16384，`/status/` 的 `app_state_copy` 就会对 8192..16383 的快照返回 0，得到「`/health` 说健康、`/status/` 说没就绪」。这与刚在 `f889d92` 修的 handler 表溢出是同一类错误（两个真相源、无断言）。

**建议修法.** ①把三个数收进一个头文件，像 `sc_route_counts.h` 那样加 `_Static_assert`；②渲染失败要能被 HTTP 面感知——至少让 `/health` 反映「本轮未发布」，否则监控看不到；③真正的减重应放在 `nekotrak` 子树（见 F2）与 `SC_RAW_JSON_LEN`，而不是继续加大缓冲。

## F2 — 透传子树超限被静默丢弃

**症状.** `nekotrak.pet` / `nekotrak.pomodoro` 是原样透传的 JSON 子树，缓冲 `SC_RAW_JSON_LEN = 448`。子树序列化后超过 447 字节时，**整个字段消失**：`has_pet = 0`，输出里没有 `pet` 键，`error` 仍是 `null`，日志里没有任何痕迹。

**实测阈值**（tale 长度 → 结果）：

| tale 字节 | 序列化子树 | `has_pet` |
| --- | --- | --- |
| 400 | 411 | 1（保留） |
| 430 | 441 | 1（保留） |
| **440** | **451** | **0（丢弃）** |

**这不是理论问题.** 参考机上真实的 `pet` 已经是 **309 字节**（`{"name":…,"lastEvent":{"at":…,"category":"fight","categoryLabel":"战斗","summary":…}}`，含中文）。到 447 只剩 **138 字节**余量——`summary` 再长一点或多一个事件，这个字段就会无声消失。这与 `firmware/esp32/README.md` 里「原样透传」的说法冲突。

**最小复现.** `test_bug_raw_passthrough_drop`：440 字节 tale → 断言 `has_pet`，实测为 0。

**根因.** `sc_wire_parse.c` 在子树放不进 `pet_json[SC_RAW_JSON_LEN]` 时选择了「跳过」，而不是截断成合法 JSON、或至少置一个 `error`／记一行日志。

**建议修法.** 三选一，但必须显式：①按真实需要提高缓冲并由 PSRAM 承担（`nekotrak` 已经是最大的一块）；②放不下时保留 `{"truncated":true}` 之类的标记，让消费方能分辨；③把 pet 降级成平面字符串字段。**弃权（静默丢弃）是最差的选项。**

## F3 — 截断劈开 UTF-8，转义层补 `\uFFFD`

**症状.** 所有字符串字段存进 `char v[SC_STR_LEN]`（96），按**字节**截到 95。多字节字符被劈开时，转义层把每个残留字节变成一个 `\uFFFD`：

| 输入 | 存了 | 转义后 | 后果 |
| --- | --- | --- | --- |
| 「日」×32（96 B） | 95 B（31 整字 + 2 残字节） | `\u65E5`×31 + `\uFFFD\uFFFD`（198 B） | 31 个真字 + 2 个替换符 |
| 🐾×32（128 B） | 95 B（23 整字 + 3 残字节） | `\uD83D\uDC3E`×23 + `\uFFFD`×3（294 B） | 1 个字变 3 个替换符 |

输出仍是合法 JSON（不会破坏解析器），但内容被改写且长度膨胀 2–3 倍。中文 `displayName` / `error` / `currentGame` 都可能踩到。

**最小复现.** `test_bug_utf8_truncation_mojibake`：喂 96 字节 CJK，断言转义结果里没有 `\uFFFD`，实测 2 个。

**建议修法.** 截断按 UTF-8 字符边界回退（丢整字而不是丢半字），或把 `SC_STR_LEN` 改成按字符计数。

## F4 — `.NET-style Trim()` 名不副实

**症状.** `sc_core.h` 对 `sc_str_set` 的注释写着 ".NET-style Trim()"，实际只剪 ASCII 空白。.NET 的 `string.Trim()` 按 Unicode 空白剪，包含 `U+00A0`（NBSP）与 `U+3000`（表意空格）。

**实测.** 输入只有两个 NBSP（4 字节）→ 固件 `has = 1`（字段存在）；同一输入在 daemon 侧 `Trim()` 后为空 → 渲染成 `null`。U+3000 同理（6 字节 → 仍然存在）。

**影响.** 同一份设备数据在两种实现里产生不同字节，直接违背「字节级兼容」。触发条件需要异常输入（纯 Unicode 空白的字段），所以定 P2 而非 P1。

**最小复现.** `test_bug_unicode_trim`（两条断言）。

**建议修法.** 补上 Unicode 空白集合（至少 NBSP、U+2000–200A、U+3000、BOM），或把注释改成「ASCII trim」并接受这一处已知分歧——但不能既声称一致又不一致。

## F5 — `/health` 就绪判定与 daemon 不一致

**症状.** `sc_health_evaluate_json` 的注释说它 "Mirrors StatusServer.cs"，但 cJSON 容忍尾部垃圾，而 daemon 用的 `System.Text.Json` 不容忍。

**实测**（同一份 `run/status.json` 内容）：

| 内容 | daemon `/health` | 固件 |
| --- | --- | --- |
| `{"devices":[]}` | 200 | 200 |
| `{"devices":[]}` + 尾随空行 | 200 | 200 |
| 重复键 `{"devices":[],"devices":[]}` | 200 | 200 |
| **`{"devices":[]} trailing`** | **503** | **200** |

**影响.** 低——快照是程序写的，不会带尾部垃圾。但它证明「两处实现 mirror」这句话没有测试支撑，而就绪判定是守护脚本唯一依赖的信号。

**最小复现.** `test_bug_health_trailing_garbage`。

## F6 — 文档说「任何非 GET → 405」，HTTP.sys 先给你 411 + HTML

**症状.** `POST`、`PUT` 在不带 body **且不带 `Content-Length`** 时，请求在进入应用之前就被 HTTP.sys 拒绝：

```text
HTTP/1.1 411 Length Required
Content-Type: text/html; charset=us-ascii      <- 不是 application/json
Server: Microsoft-HTTPAPI/2.0
Connection: close
<344 字节的 HTML 错误页>
```

没有 `Access-Control-Allow-Origin`，没有 `Cache-Control: no-store`——两个「每个响应都带」的头在这里缺失。daemon 日志里看不到这次请求，说明应用根本没被唤醒。

**对照矩阵**（实测）：

| 请求 | 结果 |
| --- | --- |
| `POST /status/`（无 body、无 CL） | **411 + HTML** |
| `POST /nope`（无 body、无 CL） | **411 + HTML** |
| `PUT /health`（无 body、无 CL） | **411 + HTML** |
| `PUT /nope`（无 body、无 CL） | **411 + HTML** |
| `POST /status/`（`Content-Length: 0`） | 405 + JSON |
| `POST /status/`（JSON body） | 405 + JSON |
| `POST /status/`（chunked） | 405 + JSON |
| `PATCH` / `DELETE` / `OPTIONS` / `HEAD` | 405 + JSON |

`curl -X POST` 正是「无 body 无 CL」的典型调用方式，所以照着文档验证契约的人会撞上它。PowerShell 的 `Invoke-WebRequest -Method Post` 会自动补 `Content-Length: 0`，因此看不到——这也解释了它为什么一直没被发现。

**定性.** 这是**文档缺陷，不是应用逻辑缺陷**：拦截发生在 `HttpListener` 之下，`StatusServer.cs` 无法感知或改写该响应。要真正修复只能换 HTTP 栈（Kestrel / 原生 socket），代价远大于收益。

**建议修法.** 在 `docs/guide/http-api.md` 的路由表下加一条明确说明：`POST`/`PUT` 必须带 `Content-Length`（哪怕为 0）；否则 HTTP 栈返回 411 HTML，且该响应不含 CORS/缓存头。同时把「每个响应都带四个头」改成「每个由本进程生成的响应都带」。

## 已验证正确的部分

这些不是「没测到问题」，是**明确验过没问题**：

**daemon 契约面（黑盒，31 项通过）**

- 路由与大小写：`/status/` 200；`/status`、`/health/`、`/Health`、`/STATUS/` 全 404；查询串与片段被忽略。
- 方法语义：`PATCH`/`DELETE`/`OPTIONS`/`HEAD` 与非空 `POST`/`PUT` 全部 405 + `{"error":"method not allowed"}`；未知路径 + 非 GET 也是 405（方法先于路径判定）。
- 响应头：`Access-Control-Allow-Origin: *`、`Cache-Control: no-store`、`Content-Type: application/json; charset=utf-8` 齐全；`Content-Length` 与 body 字节数逐一相符（3050 = 3050）。
- 响应体：404/405 精确单行；`/health` 严格匹配 `^\{…\}$`；三个响应都**无尾换行**（末字节均为 `}`）。
- 就绪状态机：删掉快照 → 双 503 且 `/health` 四键全 null；`{oops` → `/health` 503 而 `/status/` 200（文档刻意保留的不一致）；`devices` 为对象 / `null` / 字符串 / 顶层数组 / 纯空白 → 全部 503；`{"devices":[]}` 无 `schema`/`generatedAt` → 200 且两字段为 `null`（文档承诺的行为）。
- 并发：20 个并发 `GET /status/` 全 200，随后仍 200。
- 真实快照：`\u672A\u77E5\u673A\u578B`、`\u2694\uFE0F\uD83D\uDE3E` 转义正确，13 键齐备。

**Python 采集层**

- 键名大小写严格：`consoles` 被静默忽略、`IPhone` 生效（与文档一致）。
- `Consoles: 3` 在 `build_collectors()` 抛 `TypeError`，整轮失败——文档已明确警示。
- 条目级错误隔离：一个坏 `Consoles` 条目 → 1 条 invalid row，好条目照常注册。
- `BleDevices` 非 list 被忽略；缺 `address`/`nameFilter` 得 `BLE 配置缺少 address 或 nameFilter`。
- `sanitize_ports`：默认 `(9295,3074,80,443)`、去重、越界丢弃、bool/字符串跳过、空列表关掉 TCP 阶段、11 个截到 8。
- `as_bool` 的 8 种真值/假值写法与 `'garbage'` 回落全部符合文档。
- 坏 JSON / 尾逗号 → `load_config` 返回空配置（不抛），与「不阻断采集」的承诺一致。
- invalid row 是 **11 个 collector 字段 + `transport`**（不是快照的 13 键）——与 `schema/status-contract.json` 的分层设计一致。

**C# daemon**

- `RefreshIntervalSeconds` 重置语义实测：`4 → 30`、`3601 → 30`、`5 → 5`（通过真实启动日志的「轮询间隔 N 秒」读取）。

**脚本/工具**

- `pc_feed_relay.py` 只放行 `GET /status/` 与 `GET /health`；`GET /control/status` → 404、`POST`/`PUT`/`DELETE` → 405 JSON。与固件 README 与 SECURITY.md 的承诺一致（它确实把快照暴露到 `0.0.0.0`，这是它存在的目的，文档已写明）。
- `host-test.ps1`、`build.bat`、两个 dotnet 命令、Python unittest 命令均可直接执行。

## 我自己的探测错误（记录以免被误读为产品缺陷）

第一版探测报了 10 个「失败」，复核后**全部是我打错层或比较器有误**，已全部纠正：

| 误报 | 真相 |
| --- | --- |
| `RefreshIntervalSeconds=4` 在 Python 层未被改成 30 | 钳制在 C# 侧，Python 不参与；实测 daemon 就是 30 |
| `tcpPorts` 未被截到 8 | 归一化在 `lan_probe.sanitize_ports`，不在 `load_config` |
| 尾逗号未被拒绝 | `load_config` 捕获异常后返回空配置，正是文档承诺的行为 |
| `BleDevices={}` 未被忽略 | 过滤在 `build_collectors`，不在 `load_config` |
| `sanitize_ports` 5 项不符 | 它返回 **tuple**，我拿 list 比较；值全部正确 |
| invalid row 不是 13 键 | collector 层契约就是 11 字段 + transport，13 键是快照层 |
