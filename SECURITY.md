# Security Policy

## Supported versions

StatusCast is currently an early-stage desktop application. Security fixes are applied to the latest `main` branch and the latest release.

## Reporting a vulnerability

Please use GitHub's private vulnerability reporting for this repository rather than opening a public issue.

Include:

- affected version or commit,
- Windows version,
- steps to reproduce,
- expected and observed behavior.

The HTTP API binds to `localhost` only; never expose port `5099` to an untrusted network without adding authentication and a reverse proxy.

## LAN collectors (consoles, Mac / Linux nodes)

Console probes (C1) only send ARP, ICMP and TCP connect traffic on the local subnet (the TCP port probe opens a bare connection and sends no application payload). SSH node collectors (C2b) use the Windows OpenSSH client with `BatchMode=yes` (key-only, no interactive prompts), `ConnectTimeout=2`, and a hard 8 s cap per node.

Private keys stay outside the repository; `config.json` may record a key path but never a secret itself, and `run/` state is git-ignored. `sshKey` supports `~` and `%VAR%` expansion; a path that does not exist is a configuration error (no silent fallback to a default key).

Host keys use trust-on-first-use (TOFU): `StrictHostKeyChecking=accept-new` trusts the first-seen key automatically and writes it to `known_hosts`, so a later key change is rejected, but the first connection is not authenticated against a pinned fingerprint. An active MITM on that first connection would not be detected — add nodes only on a trusted LAN, or verify / pre-seed the host key out of band before the first run. `IdentitiesOnly=yes` makes the client offer only the configured key instead of every key the holding agent may expose.

Connection errors surface in the device `error` field only (stderr first line, truncated to 160 characters); BatchMode auth failures print "Permission denied" and never echo credentials. Treat node targets like any SSH entry point: add nodes only on networks you trust, keep sshd key-only, and prefer LAN addresses.

## Fallback transports

Fallback channels trade data completeness for liveness, and they do not widen the trust boundary:

- `adb pair` pairing codes are single-use for the current pairing round. They are never written to logs, snapshots, error messages or any file. Pairing material generated by `adb` stays with the local adb server; StatusCast persists none of it.
- LAN probes for iPhone, Android, consoles and nodes only send ARP, ICMP and TCP SYN (or a plain TCP connect). They carry no credentials, read no response payload, and only infer that a host is reachable.
- The experimental Wi-Fi data channel (`wifiDataChannel`) is off by default. When enabled it relies on the local usbmuxd / Apple services and Bonjour/mobdev2, using the existing Apple pairing records only.
- Degraded-online never relaxes authentication: SSH still requires key-only auth with TOFU, `adb` still requires the local adb server authorization, and a successful LAN probe grants no access to the device.
- A fallback round only reduces reported data (battery/model may be `null`); it never increases what StatusCast can read or expose.

## BLE devices

BLE peripherals (`BleDevices`) are read-only clients: StatusCast scans for advertisements and, for whitelisted devices only, connects and reads the public GATT Battery (`0x180F` / `0x2A19`) and Heart Rate (`0x180D` / `0x2A37`) characteristics.

- No pairing, bonding or write operations are performed; nothing is persisted to the Windows pairing store.
- The only device identifiers kept are the addresses and advertised names written in the local `config.json`. Nothing about discovered devices is logged or sent over the network.
- Scanning exposes nearby advertisements to the process, but only configured devices are connected to; every other advertisement is discarded after matching.
- When `bleak` is missing, only the BLE entries report an error; every other collector keeps working.
